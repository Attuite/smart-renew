## 0. 2026-08-27 母版化重构状态

报告模板已升级为 `3.0.0`，生成目标由“AI 自由撰写项目报告”调整为“绵阳范例母版 + 项目事实槽位替换”。

- 自动报告只保留工作概述、体检指标体系、社区维度、住房维度、综合研判、整治对策与行动建议和附件。
- 城区、街区、居民问卷、上一年度整改、项目库等本项目不涉及的章节不再生成。
- 社区 12 项、住房 10 项指标由计算引擎自动展开为 22 个正式分项模块，每项包含“体检内容、评价口径、数据来源、评价结果”。
- AI 只改写 7 个母版槽位：项目概况、社区总评、住房总评、社区研判、住房研判、整治对策、行动建议。
- 7 个 AI 槽位都已配置独立的范例小节参考；每次调用只向模型发送当前小节的范例结构、项目事实和数据边界。
- 提示词要求按“总体判断—分项事实—问题解释—数据边界或治理含义”形成 3 至 6 个自然段，不允许自由增加章节或引用绵阳事实。
- 全部生成改为“按二级小节串行调用、单小节校验、成功后立即保存”；个别小节失败时，已成功内容不会丢失。
- 未生成、旧草稿不兼容或局部生成失败时，系统会显示基于项目事实的母版兜底正文，不再出现“该母版槽位尚未生成项目文本”空白小节。
- 草稿按模板版本隔离，旧 `2.2.0` 文本不会混入 `3.0.0`；升级后需要重新生成全部项目化段落。
- 前端将区块标记为“范例母版固定内容”“版本数据自动填充”“指标引擎自动展开”“母版槽位 AI 改写”，便于演示和人工复核。
- 报告中的 9 张数据表已分别映射范例版式：项目信息表、体检范围表、指标体系总表、社区/住房评价结果表、社区/住房附件汇总表、住房问题整治清单和来源索引表。
- 指标体系表按“维度—分组—序号—指标项”生成合并单元格；问题整治清单按范例扩展为 9 列，缺少责任单位等数据时明确显示“待明确”。

本地真实项目接口已验证返回 7 个新章节、7 个 AI 槽位和 22 个指标分项；浏览器检查确认自动报告中不再出现城区维度。

当前演示数据仍有两项必须在正式演示前处理：社区分析中心与项目中心约相差 9 km；唯一住房正式问题为测试数据且未绑定楼栋。模板和生成链路可用，但这些数据不能作为真实项目结论。

## 1. 当前结论

当前系统已经具备自动生成“住房维度 + 社区维度”数据驱动报告草稿的主链路：

1. 从项目档案、住宅台账、照片、已归档分析、正式问题和社区分析读取数据。
2. 按第 07 步指标库编码计算住房与社区指标。
3. 创建不可变的报告版本快照，固定数据截止时间和来源编号。
4. 自动填充报告表格，并调用 AI 按范例报告二级目录生成叙述段落。
5. 校验 AI 返回的区块、数字、证据引用和段落长度。
6. 支持生成全部 AI 小节，也支持只重新生成一个二级小节。

目前产物定位为“可审阅的项目级报告草稿”，尚不能视为与绵阳范例同等完整、可直接交付的正式 Word/PDF 报告。主要限制是部分调查和空间数据尚未接入，以及尚无正式文档排版导出链路。

## 3. 已实现的数据链路

```text
项目档案 / 小区楼栋台账
          +
现场照片 → AI 候选识别 → 人工确认或修正 → 已归档分析 → 正式问题
          +
社区维度地图设施分析
          ↓
住房与社区指标计算引擎
          ↓
报告版本快照（数据、指标、来源编号、截止时间）
          ↓
固定模板 + 自动表格 + AI 叙述
          ↓
数字和证据校验
          ↓
可审阅的报告草稿
```

图片识别结果只有在人工确认或修正、归档并形成正式问题后，才进入报告统计。候选问题不会直接计入指标和报告结论。

正式问题的证据链可以包含：

- 正式问题编号；
- 分析批次编号；
- 原始照片编号；
- 标注照片编号；
- 问题编码；
- 第 07 步指标编码。

## 4. 指标计算现状

### 4.1 住房维度

指标定义使用 `IND-HOUSE-001` 至 `IND-HOUSE-010`。

| 指标 | 当前状态 | 计算口径 |
| --- | --- | --- |
| 结构安全隐患 | 可计算 | 按 `buildingId` 去重的正式问题楼栋数 |
| 燃气安全隐患 | 可计算 | 按 `buildingId` 去重的正式问题楼栋数 |
| 楼道安全隐患 | 可计算 | 按 `buildingId` 去重的正式问题楼栋数 |
| 围护结构安全隐患 | 可计算 | 按 `buildingId` 去重的正式问题楼栋数 |
| 非成套住宅 | 部分可用 | 当前没有户级对象编号，只能统计正式问题记录，不能推算套数 |
| 管线管道破损 | 可计算 | 按 `buildingId` 去重的正式问题楼栋数 |
| 适老化改造需求 | 暂无数据 | 当前识别与调查流程未覆盖 |
| 入户水质不达标 | 暂无数据 | 当前流程未接入水质数据 |
| 节能改造需求 | 暂无数据 | 当前识别与调查流程未覆盖 |
| 数字化改造需求 | 暂无数据 | 当前识别与调查流程未覆盖 |

住房问题占比的分母固定为“已归档分析覆盖楼栋数”，不代表项目全部楼栋。计算规则包括：

- 同一楼栋同一指标的多条正式问题按楼栋编号去重；
- 缺少已归档分析覆盖楼栋时，不生成无依据的比例；
- 问题缺少楼栋编号，或问题楼栋不在调查范围内时，指标状态降为 `partial`；
- 暂无数据的指标不得表述为 0、达标、优良或无问题；
- 当前不生成历年趋势、整改成效或优良等级。

### 4.2 社区维度

当前接入 12 类社区设施，参考第 07 步指标库 `IND-COMM-011` 至 `IND-COMM-022`：

1. 养老服务设施；
2. 婴幼儿照护设施；
3. 幼儿园；
4. 小学；
5. 停车设施；
6. 新能源汽车充电设施；
7. 电动自行车充电设施；
8. 公共活动场地；
9. 步行空间；
10. 垃圾分类设施；
11. 物业管理服务空间；
12. 智慧设施。

当前社区数据来自地图 POI 检索和空间合并，结果类型为 `proxyObservation`。它只能说明“检索到的设施空间数量”，不能直接生成以下结论：

- 配建达标或不达标；
- 服务覆盖率；
- 设施缺口；
- 15 分钟步行可达率；
- 服务盲区；
- 设施建筑面积是否合规。

没有社区维度分析，或者项目保存的是街区维度分析时，相关指标状态为 `unavailable`。

## 5. 报告模板和生成策略

模板版本为 `3.0.0`，按绵阳范例报告的第二层级拆分，但只保留本项目涉及的住房与社区内容。每个区块有三种处理方式：

| 区块类型 | 数据来源 | 用户操作 |
| --- | --- | --- |
| `fixed` | 模板预置文字 | 不重新生成 |
| `variable-table` | 报告版本快照 | 自动填充 |
| `ai-narrative` | 报告事实包 + AI | 可按二级小节重新生成 |

需要 AI 项目化改写的 7 个槽位为：

- 项目概况；
- 社区维度总体情况；
- 住房维度总体情况；
- 社区维度综合研判；
- 住房维度综合研判；
- 分类整治对策；
- 近期、中期和持续性行动建议。

每个 AI 槽位在 `report-template.json` 中都有 `reference.section` 和 `reference.content`，用于向模型传递对应范例小节的论证顺序和段落密度。城区、街区、居民问卷、上一年度整改和项目库等本项目不涉及的章节已从自动报告中移除。

## 6. API

### 6.1 生成报告版本快照

```http
POST /api/reports/generate
Content-Type: application/json

{
  "projectId": "项目编号",
  "generatedBy": "报告生成人员"
}
```

当前生成版本快照前，项目至少需要一条人工确认的正式问题。

### 6.2 生成或重新生成 AI 草稿

```http
POST /api/reports/{reportId}/draft
Content-Type: application/json

{
  "subsectionIds": []
}
```

- `subsectionIds` 为空：生成或重新生成全部 AI 小节。
- 指定二级小节，例如 `["housing-indicator-analysis"]`：只替换该小节，其他已生成内容保持不变。
- 全部生成时服务端对每个二级小节分别调用模型、校验和保存，返回的 `generation.completed` 和 `generation.failed` 可用于显示局部成功状态。

### 6.3 读取草稿

```http
GET /api/reports/{reportId}/draft
```

返回的 `document` 已经组装固定内容、快照表格和 AI 段落，可直接交给前端展示。即使尚未生成 AI 草稿，该接口也会返回 7 个带项目事实的 `template-fallback` 段落，不会返回空白小节。

## 7. AI 调用和校验规则

本地服务和 CloudBase 函数使用以下环境变量：

```text
DASHSCOPE_API_KEY
DASHSCOPE_BASE_URL（可选）
DASHSCOPE_MODEL（可选）
DASHSCOPE_REPORT_MODEL（可选，优先用于报告叙述）
```

不得把实际 API Key 写入代码、GitHub、Markdown 或前端长期存储。

提示词要求模型：

- 只能依据报告事实包写作；
- 每个小节必须参考自己的 `reference`，但不得复制范例城市的名称、数字和结论；
- 不得使用绵阳范例中的具体城市事实；
- 不得自行计算或补齐数字；
- `partial` 指标必须说明限定口径；
- `unavailable` 和 `invalid` 指标不得写成 0、达标或优良；
- 社区 POI 代理观测不得写成覆盖率、缺口、达标或服务盲区；
- 每个区块至少提供一个来源编号或 `FACT:` 事实路径；
- 不得虚构资金、责任单位、政策依据和工期。

服务端会校验：

- AI 返回的 JSON 格式；
- 区块数量和区块编号；
- 是否存在重复、未知或遗漏区块；
- 段落数量与长度；
- 文本中的数字是否已存在于事实包；
- 证据引用编号或事实路径是否真实存在。

校验可以显著降低编造风险，但不能代替最终人工审阅。

## 8. 前端操作流程

建议按以下顺序验证完整链路：

1. 创建或选择项目，补齐小区、楼栋和住户台账。
2. 在住房维度上传现场照片并调用视觉模型。
3. 人工确认、修改或驳回候选问题。
4. 归档分析并确认正式问题已入库。
5. 在社区/街区维度选择“社区维度”，完成定位、设施检索并保存分析。
6. 在报告页面填写复核人员。
7. 点击“生成报告版本快照”。
8. 系统继续生成 AI 草稿并切换到“AI 报告草稿”视图。
9. 检查指标状态、数据口径、证据引用和警告。
10. 如需修改叙述，点击对应二级小节的“重新生成本小节”。

报告页面目前可以查看：

- 完整报告范例原文；
- 当前项目动态报告；
- 固定版本 AI 草稿；
- 住房与社区指标表；
- 正式问题与整治建议清单；
- 来源数据编号。

## 10. 当前限制与风险

### 10.1 数据能力限制

- 住房 10 项指标中，5 项可以形成楼栋数和调查范围内占比，1 项只能形成问题记录，4 项暂无来源数据。
- 社区 12 项目前都是 POI 代理观测，不是标准指标的达标计算。
- 暂无居民问卷、访谈、历年数据和整改前后对比。
- 暂无居住用地、步行路网、设施服务半径和设施建筑面积数据。
- 尚未形成独立的社区维度正式问题及整治清单。

### 10.2 产品和交付限制

- 当前输出是网页中的报告草稿，尚未自动导出正式 Word/PDF。
- 尚未实现目录、页码、页眉页脚、图表、地图和照片的正式排版。
- 范例报告原文用于结构和写作参考，当前固定文字是精简后的项目级模板，不是对范例全部长文本的逐段复制。
- AI 校验主要覆盖结构、数字和引用，专业结论仍需人工审阅。

### 10.3 工程限制

- `index.html` 和两个 API 入口文件较大，本地与 CloudBase 路由存在重复实现，后续修改要同步核对。
- 报告模板在 JSON 文件和 `report-narrative-core.js` 的后备模板中各有一份定义。调整章节时应优先修改 JSON，并确认后备模板不会产生行为差异。
- 旧的 `SESSION_HANDOFF.md` 包含历史分支和目录信息。本次报告功能以本文档和当前 Git 状态为准，不应直接照搬旧分支约定。

## 11. 下一步建议

建议按以下优先级继续：

### P0：形成真正可交付的第一版报告

1. 将报告生成入口收敛为“住房 + 社区”范围，隐藏与当前目标无关的城市、街区长篇空章节，或提供精简版模板。
2. 增加报告生成前的数据完整性检查页面，逐项显示台账、归档分析、正式问题、社区分析和 API 配置是否就绪。
3. 增加 Word/PDF 导出，完成标题、目录、二级标题、表格、图表、地图、照片和来源编号排版。
4. 为指标计算、事实包、AI 校验和局部重生成补充自动化测试。

### P1：提高住房报告完整度

1. 为非成套住宅增加户级对象或套数调查字段。
2. 接入适老化、水质、节能和数字化调查字段。
3. 明确每项指标的调查对象、有效样本和分母生成规则。
4. 增加按小区、楼栋和问题类型的图表与照片证据页。

### P2：提高社区报告完整度

1. 接入居住用地边界和面积。
2. 接入步行路网和设施服务半径，计算覆盖面积与服务盲区。
3. 接入设施建筑面积、服务能力和配建标准，形成真正的达标判断。
4. 将社区设施短板转化为可复核的社区问题及整治清单。

### P3：增强报告治理

1. 保存人工编辑后的最终稿，并区分 AI 草稿、审核稿和发布稿。
2. 增加报告审核记录、修改说明和版本差异。
3. 将指标口径、模板版本和模型版本展示在导出报告附录中。

## 12. 接力开发注意事项

- 开始开发前先执行 `git status --short --branch`，确认位于预期分支且工作区干净。
- 不得把 `.env`、API Key、`.smart-renew-data/`、`tmp/`、`node_modules/` 或本地上传文件提交到仓库。
- 不得让 AI 候选问题直接进入正式指标统计。
- 不得把地图 POI 数量解释为标准配建、覆盖率或服务盲区。
- 不得使用项目总楼栋数替代已归档分析覆盖楼栋分母。
- 本地 `server.mjs` 与 CloudBase `functions/api/index.js` 的报告行为必须保持一致。
- 修改报告章节、指标定义或提示词后，至少验证完整生成和单小节重新生成两条路径。
- 部署不属于本分支推送操作；只有用户明确要求上线时才执行 CloudBase 部署。
